# 发布 #14 探针失败恢复

## 事实与边界

`ee8e78c` 的发布 #14 报告 failure_code=`runtime_probe_failed`。user、developer-api、
comms 为 rolled_back，history、conversation 为 planned。只读复核确认五个服务
均回到原镜像、RUNNING、健康 200，设备限制仍为 true；comms 尚未运行 #114 修复。
迁移和环境变量未被该发布修改。

旧脚本在 RUNNING 后首次执行探针失败时立即抛错并回滚，没有保留具体执行退出码
或探针阶段。移除的候选容器运行日志已不可读；构建日志未出现本次筛选的构建错误。
这些证据能定位脚本失败边界，不能还原底层究竟是进程执行、健康请求还是容器切换。

## 修复

- 在原 240 秒轮询窗口内，有界重试只读进程执行、输出暂缺和健康请求失败。
  不重放更新 Dockerfile 或 redeploy 的写操作；不放宽健康、源码或开关匹配。
- 源码读取错误、非法开关、配置漂移、FAILED/CRASHED/CANCELED 部署仍拒绝。
  持续失败保留最后的安全阶段/退出码/匹配结果，并按原逻辑回滚。
- 计划名称由实际 plan job 输出保存，下载使用该 producer 的输出。
  报告名称包含 run_attempt，保留每轮失败证据，支持只重跑 deploy。
- CLI 显示安全 failure_code，报告不写原始输出、私有 URL、Dockerfile 或密钥。

## 验证与发布

新增测试先复现旧行为：一次执行失败即中止，持续失败缺少诊断上下文。
再覆盖瞬时恢复、持续失败超时回滚、源码/开关/健康不匹配、终态部署立即拒绝、
不重放写操作、真实 Node 探针错误去敏，以及 plan producer 尝试名称保留。

合并后应由新提交的检查和镜像生成新发布，再人工批准 production。
发布后核对报告、实际源码和会话凭证来源，并继续 #114 的超过 3 分钟对话验收。
